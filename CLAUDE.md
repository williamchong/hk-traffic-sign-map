# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Commands

`pnpm` is broken in this environment — always use `corepack pnpm`.

- `corepack pnpm dev` — dev server (http://localhost:3000)
- `corepack pnpm lint` / `corepack pnpm typecheck` — must both pass before any commit
- `corepack pnpm generate` — static build to `.output/public`; also used as the final pre-commit gate (it exercises the SSR/prerender path the dev server doesn't)
- `corepack pnpm data:build` — fetch TD GML + derive face bearings + (re)build `public/data/traffic-signs.pmtiles`, then the road-rules overlay
- `corepack pnpm data:road-rules` — tile the Road Network v2 rule extents (`SPEED_LIMIT`, `BUS_ONLY_LANE`, `PROHIBITION` joined onto its `CENTERLINE` route, `NSR` no-stopping, `PEDESTRIAN_ZONE`) plus the two non-IRNP layers — derived `cutoff` (roads public light buses cannot enter at all) and curated `taxi` (which colour of taxi may serve a road) — into `public/data/road-rules.pmtiles` (~5.2 MB, 12 s; the taxi layer is ~1.3 MB of that). Standalone; only needs `data/raw/RdNet_IRNP.gdb.zip` from `data:fetch`. Writes its own `rulesVersion` key into `app/data/tilesVersion.json`. Prints the per-kind tally, the REMARKS heads that fell to `other`, and NSR's per-code tallies (`veh` · `tz` · `eday`, against the counts recorded beside `NSR_VEHICLE_TYPES` in `sign-layers.mjs`) and the cut-off layer's inputs and largest areas — review those after every TD refresh (see pipeline step 5). It also prints the taxi layer's per-colour × access tally, its straddling count and **any clause in `data/taxi-zones/areas.json` that matched no road** — a street TD renamed silently draws no band, so that warning is the one to read after every refresh
- `corepack pnpm data:catalogue` — re-extract sign pictograms + `app/data/signCatalogue.json` from the Index Plan PDFs, then `data:aliases` (suffix variants) and `data:sign-shapes` — both spawned **from inside `build-sign-catalogue.mjs`** after a write (`--commit` or a bare rebuild), never after `--propose`, which writes nothing. ⚠ Keep this npm script a **single command**: npm appends a caller's flags to the LAST command of a `&&` chain, so chaining here sent `--propose`/`--sheet` to the wrong script and silently ran a full unfiltered rebuild (`99b00b2`). **Fully deterministic, no API key, $0**: render the page from its SVG via `mutool draw -F svg` → `rsvg-convert`, read the table grid from `mutool` path geometry, `tesseract` for both the No. bind and the English Description cross-check. Extra deps: `brew install librsvg mupdf-tools tesseract`
- `corepack pnpm data:aliases` — point every installed suffix variant (`TS639L`, `TS2701U`, …) with no plate of its own at its base sign's pictogram. Needs `data/raw/DTAD_TS_ABV_PT.gml`; skips with a warning without it. Chained into `data:catalogue` (from inside the builder)
- `node scripts/audit-sign-images.mjs` — cross-check each `public/signs/<code>.png` against Road Sign Factory's plate for the same number, worst-first into a `verify.png` triage montage. Catches the one bind nothing else checks (No.↔**pictogram**; `names.mjs` only checks No.↔description). `--staged` audits a `--propose` run before it is committed; `--code`, `--top`, `--refresh`. Deliberately outside both npm chains — on demand, writes only gitignored `data/raw/`. **Their repo carries no licence: comparison oracle only, no pixel of theirs may ever ship** (see `data/sign-names/README.md`)
- `node scripts/fetch-zone-notices.mjs` — vendor TD's **prohibited-zone traffic notices** (reg 14(1)(a) of Cap. 374G; the data.gov.hk historical archive from 2021-06, ~1,130 snapshots deduped by content hash) into `data/zone-notices/prohibited-zones.json`. The only dated public record of what a public-light-bus zone covers, and it reaches back only to 2021, so it can **verify** the IRNP `PROHIBITION` rows, never replace them. Cache under gitignored `data/raw/.notice-cache`; `--feed`, `--start`, `--limit`, `--refresh`
- `node scripts/audit-cutoff-notices.mjs` — read-only audit of the cut-off layer's inputs after every TD refresh: (1) standing PLB designations whose streets carry no PLB row, with the TS119/TS522 count on them; (2) rescissions whose streets still carry a closing row; (3) PLB-coded rows with no plate within `--radius` (30 m) and plates with no row; (4) `data/zone-notices/overrides.json` entries TD has caught up with; (5) `data/zone-notices/known-zones.json` — ~50 roads every driver knows, with the status the build gave them when verified against published minibus practice (2026-09-22), so a row change on one of them is noticed. Binds a notice to streets by NAME only; the answer to a finding is a human-written override entry, never a heuristic. Needs `RdNet_IRNP.gdb.zip` + `DTAD_TS_ABV_PT.gml` from `data:fetch`
- `node scripts/audit-taxi-zones.mjs` — read-only audit of the curated taxi operating areas (`data/taxi-zones/areas.json`) against the plates TD installed: (1) every `TS329` / `TS569` terminator snapped to its nearest road and grouped by what the curated extent makes of that road — at a fringe destination, at the end of a designated route, on a boundary, or unexplained; (2) boundary roads with no terminator within `--radius` (40 m), a tally rather than an error; (3) the per-colour stand plates (`TS818` NT 358, `TS566` Lantau 28, `TS567` urban 178) that stand where their own colour may not serve — the check the terminators cannot give; (4) clauses that matched no road. **The plates are an oracle, never an input**: the answer to a finding is a human edit to `areas.json`. Needs `RdNet_IRNP.gdb.zip`, `hksar_18_district_boundary.json` and `DTAD_TS_ABV_PT.gml` from `data:fetch`. Outside both npm chains
- `node scripts/audit-sign-names.mjs` — re-run the current `verdictFor` over the `desc.en` **already in the catalogue** and report anything it would not ship today. Catches the drift `names.mjs` structurally cannot: a merge run leaves an existing code completely alone (`extract.mjs` computes the row's OCR and verdict, then discards them — no crop, no `desc` update), so a description written by an older extractor is never revisited by any rebuild — 71 rows survived three extractor generations that way. A stored `fill` desc IS the list's wording and so re-verdicts as `agree`; anything that does not is legacy. `--write` applies **only the `fill` rows** (there `ship` IS the list's wording, so it is the pipeline's own rule, not a judgment); `disagree`/`code-misread`/`no-list` are reported and left alone — only the printed sheet settles those. `--code TS438,TS452` narrows. Outside both npm chains, read-only without `--write`
- `node scripts/fetch-ruc-names.mjs` — vendor `data/sign-names/ruc.json`, the bilingual sign names TD publishes in the **Road Users' Code** chapter 8 (five sign-plate sections, `en` + `tc` editions of the same page), and cache their images to gitignored `data/raw/.ruc-cache`. The **only** public source of Chinese for these signs — the Index Plan's Description column is English-only on every sheet, so no extractor work can ever produce one. Byte-faithful to the page, typos included
- `node scripts/bind-ruc-names.mjs` — propose `SIGNID → zh` from that list and stage a `verify.png` review sheet under `data/raw/ruc-names`; `--commit [--reject TS#,TS#]` writes the approved `zh` into `app/data/signDescriptions.json`. **The Code prints no sign numbers**, so the bind is earned from the PICTURE (its image vs our `public/signs/<code>.png`, colour kept — greyscale ranks "ahead only" 9th among the blue roundels and 1st with colour), scored as cached 16×16 vectors because 262 × 1,217 comparisons at one `magick compare` each is an hour. The English caption is **corroboration only, never the bind**: the two editions share 71 image files and caption several of them with two different signs, and all three verified cases have the English wrong and the Chinese right (`102c3_n.gif` is a variable speed limit, captioned "except for access if no alternative route" — full table in `data/sign-names/README.md`). Two guards withhold on TD's own row slips — one name claimed by two codes (`shared-name`), one code claimed by two names (`collision`). Outside both npm chains; writes nothing without `--commit`
- `corepack pnpm data:stacked-icons` — re-render the in-signpost pictograms to a common width (`public/signs-stacked/`) from `public/signs/`; cheap, no VLM. Part of `data:build`; run standalone after `data:stacks`/`data:catalogue` change which signs stack
- `corepack pnpm data:sign-shapes` — classify each `public/signs/<code>.png` as a solid rectangular plate vs circle/triangle (by alpha bounding-box coverage ≥0.85) → `app/data/signShapes.json`. Cheap, no VLM; chained into `data:catalogue` (from inside the builder) so it stays in sync. The runtime shrinks lone plate signs (e.g. the blue "P") so a full-bleed square doesn't read heavier than a same-tier roundel — see Runtime invariants

There is no test suite; verification is lint + typecheck + `generate`, plus a real-browser smoke test via the chrome-devtools MCP when map behaviour changes (the map only runs client-side with WebGL).

Dev gotcha: after dependency/cache changes the Vite dep-optimizer can 504 ("Outdated Optimize Dep") and the map never mounts. Fix: kill dev, `rm -rf node_modules/.vite node_modules/.cache .nuxt/cache`, restart.

## Two runtimes — do not cross-import

`scripts/*.mjs` are Node build-time tools; `app/` ships to the browser. Shared constants (tile layer name, category/`SIGNID` conventions) are **intentionally duplicated** across the boundary rather than imported. `app/composables/useSignCategories.ts` keys must stay consistent with the category logic in `useSignCatalogue.ts`; `scripts/sign-layers.mjs` is the manifest the pipeline tags features with; `scripts/text-similarity.mjs` holds the pure normalise/Levenshtein primitives both name binds share (kept out of `catalogue/names.mjs` because that reaches `sheets.mjs`, which `mkdirSync`s the extractor's scratch dir at module load); `scripts/fetch-cache.mjs` holds the request pacer and the atomic cache write the two third-party fetchers share; `scripts/geo.mjs` holds the helpers the raw-layer scripts share (the TD CityGML regexes, `parsePolePoints`, streaming `readSignIdCounts`, one-pass `reprojectPoints` via `gdaltransform`); `scripts/catalogue/` is the Index-Plan extractor split into modules — scripts may import each other, `app/` never imports either.

## Data pipeline (build-time)

1. `fetch-data.mjs` → raw data into `data/raw/` (gitignored, resumable). Pulls the tiled `SIGN_LAYERS` (TD GML + `.gfs`) plus the build-time-only `BUILD_TIME_DATA` (each entry names its `ext` and, when it isn't a TAD resource, its `url`): **Road Network v2** as the single FGDB zip `RdNet_IRNP.gdb.zip` (17 MB for all 17 layers; the per-layer GML of `CENTERLINE` alone is 486 MB — GDAL reads the zip in place via `/vsizip/`), and `DTAD_RD_MARK_LINE` (~155 MB, the fallback bearing host). Neither is tiled.
2. `compute-bearings.mjs` → derives an **absolute POST facing** per `DTAD_TS_ABV_PT` feature (ported from `hk-taxi-Q`'s `facing_from_side`, decisions `Q62`/`Q72`). Host point = the sign's **pole** (`DTAD_TS_POLE_PT`, joined by `GG_NAME`; 94 % of signs have one) — the abbreviation point is TD's *label* position, a median 2.3 m (p90 6.5 m) from the pole. The host is snapped to the nearest Road Network v2 `CENTERLINE` segment within 25 m (read as CSV+WKT so the coordinates stay in HK1980 metres — GDAL's GeoJSON drivers reproject to WGS84 unconditionally; arcs arrive pre-stroked at ~1.5 cm (~12M vertices, 309 MB of WKT), so GDAL simplifies them on the way out with `-simplify 0.01` — a 1 cm sagitta keeps chord directions within ~2.6° of the tangent on a 10 m-radius corner while straight runs collapse to their endpoints). The centreline is *directed*: `TRAVEL_DIRECTION` 3 = travel only in the digitised direction (68 % of edges — dual carriageways are opposed one-way pairs), 1 = both ways. With `heading` = compass of the digitised direction and `z = dx·(sy−qy) − dy·(sx−qx)` (>0 ⇔ host is LEFT of travel = the nearside kerb under drive-on-the-left): **one-way edge or nearside kerb → facing = heading + 180 (the plate looks back at the traffic passing it); offside kerb of a two-way edge → facing = heading.** A ground-level pole (empty TD `ELEVATION`) whose nearest centreline is off-grade is re-hosted on the nearest at-grade one (the flyover guard; ~8k cases). Signs with no centreline in reach fall back to the old road-marking rule (tangent flipped by side — *relative* only, chainage direction unknown). Output: `data/raw/_face_bearings.json` keyed by `FEATUREID` → `[degrees, source]` (source 1 = centreline/absolute, 0 = marking/relative), plus `data/raw/_pole_anchors.json` (`GG_NAME` → `[lng, lat]`, the reprojected pole of every sign group that has one). Coverage: **97.7 % via centreline**, 1.4 % marking fallback, 0.8 % none (upright at runtime). The bearing is the way the PLATE FACES (its outward normal, toward the drivers who read it); the runtime draws the plate **tipped flat onto the map**, so `icon-rotate` is the bearing **+ 180°** and the pictogram's top points *away* from the traffic (see Invariants). This file holds the *post* facing only — the per-plate no-entry turn is applied downstream. ⚠️ **Ungraded**: no source publishes a facing (hk-taxi-Q's turn-restriction diff could not grade the kerb side either). ⚠️ **Corner poles are the known weak spot**: 57 % of hosts have a second, non-parallel road within 25 m and 30 % within 5 m of the nearest, and nothing in the data says which road a junction sign serves (a give-way's pole is 5.7 m from one street and 5.8 m from the other at the Wing Hong St / Tung Chau West St test pole) — the nearest wins, as in hk-taxi-Q. `DTAD_RD_AL_LINE` (~178 km) and `ANGLE` (see Invariants) were rejected earlier.
3. `compute-stacks.mjs` → groups `DTAD_TS_ABV_PT` by **`GG_NAME`** (the GML "sign-group" id — signs gazetted/installed together as one assembly to be read as a unit; *not* the sign type `SIGNID`, *not* the Index-Plan category). **A `GG_NAME` is one FACE of a pole**: TD draws a back-to-back pole ("Give way" toward the side street, "No entry" toward the main road — the commonest case, ~1.4k poles) as two groups whose `DTAD_TS_POLE_PT` points (same `GG_NAME` as their signs) coincide. So the script also reads the pole layer and merges every group whose pole points lie within 0.3 m into one **post** (~8.2k multi-face posts, up to 4 faces). Nothing in TD's data records which way a face points — the abbreviation `ANGLE` is a text-readability rotation (it lives in −90°…+100°), the pole `ANGLE` is unrelated to the road, and the per-member road-marking bearing is the same for both faces — so the faces are turned in **quarter turns** from the *post* facing of step 2, slotted by meaning: a face whose top sign is in `AGAINST_TRAFFIC_CODES` (`sign-layers.mjs`: `TS115`/`TS116`, the no-entry family, which addresses the wrong-way driver — hk-taxi-Q `Q72`) prefers the back (`AGAINST_TURNS` 180, 90, 270, 0), any other face the front (`FORWARD_TURNS` 0, 180, 90, 270), each taking the first turn not yet used. So a "Give way | No entry" pole shows the give-way looking back at the emerging traffic and the no-entry looking the other way, a "Taxi stand | Taxi stand" pole shows one plate per direction, and a 3-face pole reads as a crossroad, not a 120° star. A single no-entry face on an otherwise lone post is likewise turned 180 from the post facing. Face 0 is the forward face whose top sign ranks highest (no-entry faces sort last); every post anchors on its pole point when it has one (only a post with no pole record keeps its primary's label point). For each post of ≥2 **catalogued** signs (a face whose members span >15 m is dropped) it assigns a `STACK_INDEX` (0 = top — main signs first by category rank `regulatory→warning→informatory→temporary`, **supplementary always last**, `SIGNID` tiebreak; face-major, so the index is unique across the whole post). It also records, per member, the post's WGS84 anchor (reprojected via `gdaltransform`), its **face's** `FACE_BEARING`, the member's pictogram pixel width, its **`STACK_OFF`** — the baked, per-member cumulative *centre offset* down its face's column (icon source-px; face 0's top sign centred on the anchor, the rest hanging below; every other face's column starts past that anchor plate's half-height so it clears it whichever way it points) — the post's **`primaryTier`** (the primary sign's tier, so the runtime sizes the whole post as one unit and the plates keep their real-life ratio) and its **`stackId`** (face 0's `GG_NAME` — the runtime groups by it, since a multi-face post spans several `GG_NAME`s). Output: `data/raw/_sign_stacks.json` keyed by `FEATUREID` → `[index, size, picWidth, anchorLng, anchorLat, bearing, stackOff, primaryTier, stackId]` (~78k signs across ~34k posts; tallest post 9, max offset ~576 px). The 15 m span cap drops pathological `GG_NAME`s reused across signs kilometres apart. Real-assembly members sit ~4 m apart (median — they're the drawing's label points, ~2.3 m from the pole); to draw a rigid post the build **collapses them onto the pole + their face's bearing** (see step 4) — i.e. every sign is drawn where its pole was surveyed, not at TD's label point (which is *more* true to the ground than the raw points were). **Stacked plates render at a common width** (not a common height), so within a post each plate keeps its true aspect — a wide supplementary plate comes out as a short wide bar under a taller main sign. The offset maths use the plate heights in that common-width space (`COMMON_WIDTH × picH / picW`), with offsets quantized to `OFFSET_STEP` (8 px, must match the runtime's `icon-offset` match grid). `STACK_OFF` is `[0,0]` for the top member and grows downward; non-stacked signs never carry it. **`gen-stacked-icons.mjs`** (run right after this in `data:build`) re-renders exactly the in-post pictograms (`signGroups.json` keys) to that common width → `public/signs-stacked/<CODE>.png`, the set the runtime swaps in for stacked members. Same fall-through contract as bearings: missing file → signs just don't stack. **Also emits `app/data/signGroups.json`** (`{ SIGNID: [stackId, …] }`) over the **same** stacked posts — the runtime sign-ID filter uses it to expand a match into its whole signpost (see Runtime architecture). Built here because this is the one place assembly membership is known.
4. `build-tiles.mjs` → `ogr2ogr` reprojects each layer **EPSG:2326 (HK1980 Grid) → EPSG:4326**, injects a `category` property per the `sign-layers.mjs` manifest *and* (for the `traffic-sign-abbreviation` layer only) the `FACE_BEARING` from step 2 — the post facing **+180° for a lone sign in `AGAINST_TRAFFIC_CODES`** — with `FACE_ABS` (1 = absolute centreline host, 0 = relative marking fallback), and **moves every lone sign onto its pole** from `_pole_anchors.json` + the `STACK_INDEX`, `STACK_OFF`, and `STACK_TIER` from step 3 (looked up by `FEATUREID`). For a **stacked** member it additionally **moves the geometry to the post's anchor (its pole), overrides `FACE_BEARING` with its face's bearing, and injects `STACK_ID`** — so the whole post is rigid (one coordinate, one bearing per face) in *both* archives and the runtime just lays members out along `STACK_OFF`, sizing the whole post by `STACK_TIER` (the primary's tier) (`STACK_INDEX`'s presence also flags the member so the runtime draws it from the common-width `signs-stacked` set on the dedicated `sign-stack` layer). Then `tippecanoe` packs the result into **two** PMTiles archives (source-layer `signs` in both): `public/data/traffic-signs.pmtiles` (~24 MB, **thinned** via `--drop-densest-as-needed` — the LOD overview for the unfiltered/category view) and `public/data/traffic-signs-full.pmtiles` (~46 MB, **retain-all** via `-r1 --no-feature-limit`, restricted to the abbreviation class with `-j` — the sign-ID-filter distribution view). One pyramid can't serve both because tippecanoe's feature-dropping is **filter-blind** (decided per-tile before the runtime filter is known): a thinned pyramid gives a clean overview but a filtered subset of it shows only drop-lottery survivors at low zoom (the bug behind commit `5a1ad4e`), while a retain-all pyramid fixes the filter but mushes the overview. The two archives are built from **two combined streams** so a co-located assembly reads as **one object when zoomed out and a complete signpost once zoomed in**. The overview reads `_combined_lod.geojsonl`: below `STACK_LOD_MINZOOM` (13, = `TIER_LOD[0].minzoom`) each assembly is represented by a single *thinnable* dot — its primary emitted with `tippecanoe.maxzoom 12` and no minzoom, so drop-densest thins it like any lone sign and the overview stays sparse (non-primaries aren't emitted at all below 13); from z13 up every member is emitted with an explicit `tippecanoe.minzoom`, which tippecanoe **keeps through `--drop-densest-as-needed`** (un-pinned neighbours thin instead) so no member — least of all the primary — is thinned out of the post mid-zoom. The full archive reads the plain `_combined.geojsonl` (no zoom hints) so a sign-ID filter still finds every member at every zoom. (Pinning the primary at the map floor instead was tried and rejected: ~19k always-on primaries re-crowded the default z11 overview — the marker keeps it thinnable.) The runtime swaps which source the sign layers read by `filterMode` (see Runtime architecture). One combined `?v=<hash>` (over both files' bytes) busts the byte-range cache. tippecanoe's max zoom is **pinned at `-z 15`** (MapLibre overzooms past it — fine for points). It used to be `-zg`, which guessed 15 while every sign sat at its own label point; once signs were collapsed onto shared pole anchors the guess jumped to 20 — tripling both archives (23→70 MB, 44→105 MB) with z16–20 tiles the app never requests, splitting the PMTiles directory into leaves (an extra range request per cold tile) and re-calibrating drop-densest so the z11 overview came out ~30× sparser. Never reintroduce `-zg` or `--extend-zooms-if-still-dropping`.
5. `build-road-rules.mjs` → the **road-rules overlay** `public/data/road-rules.pmtiles` (six tippecanoe source-layers `speed` · `buslane` · `prohibition` · `nsr` · `pedzone` · `cutoff`; `-Z 9 -z 15`, no rate-drop — lines) from the SAME Road Network v2 FGDB step 2 reads. **The extents are TD's own; nothing is derived from sign points.** The 2026-09 evaluation that settled this: the IRNP already publishes `SPEED_LIMIT` (4,338 lines, ~860 km, values 30/70/80/100/110 — 50 is the implicit default and has no rows), `BUS_ONLY_LANE` (251 lines with free-text `TIME_ZONE` + 8-char `EFFECTIVE_DAY` Mon..Sun+PH mask), `PROHIBITION` (2,341 *points at the sign* each naming, by `ROAD_ROUTE_ID`, the whole `CENTERLINE` route it governs — all join), `NSR` (20,046 no-stopping lines, own geometry, **no route id**) and `PEDESTRIAN_ZONE` (66 lines, bus-lane-shaped: free-text hours + day mask, joined by `ROAD_ROUTE_ID`). Sign points corroborate it (90–99 % of TS173/175/176/177/197, TS119, TS130 sit within 15 m of their matching feature) but could never replace it: 26 % of 70 km/h segments and 64 % of bus-lane segments have no sign within 30 m — a limit is posted once and runs for kilometres. Mechanics: one `ogr2ogr -f GeoJSONSeq … -t_srs EPSG:4326 -dim XY -select …` per layer (**`-dim XY` is mandatory** — those layers are measured XYM geometries and tippecanoe reads M as elevation), then `CENTERLINE` as **two reads** — names, `OBJECTID`, `TRAVEL_DIRECTION` and the four `ST_StartPoint`/`ST_EndPoint` coordinates for every route through `-dialect SQLite` (1 s, concurrent with a SQLite read of `TURN`; that `SELECT` never serialises a line, where any OGR-SQL/`-select`/`-nlt NONE` read decodes, reprojects and serialises all 36k pre-stroked routes, ~400 MB / ~10 s), and line geometry for only the prohibition routes (read beside it) and the cut-off edges (after the cut-off pass names them; ~6.8k together) via OGR `-where "ROUTE_ID IN (…)"` with `-simplify 0.01`, **in concurrent chunks of 2,000** (OGR's where-parser exhausts its memory on one ~6k-id list; the same IN list under `-dialect SQLite` took 272 s — never move it there; the 1 cm simplify, as in step 2, turns 54 MB of stroked-arc JSON into 1 MB, which tippecanoe then re-reads once per prohibition `kind`). The names read yields street names for every feature **and**, unfiltered, a `ST_CODE → name` map for NSR, which names its roads by `ST_CODE_1..6` instead of a route (19,849 / 20,046 rows resolve on `ST_CODE_1`; ~5.8k codes, names only, so holding them all is free). NSR is read **last and streamed straight through** — it needs nothing buffered, and at 20k features it outweighs the other layers together. Its three descriptive fields are **coded integers**, not text: `VEHICLE_TYPE` → `veh` mapped onto TD's own vehicle codes (`ALL`/`TX`/`PLB`/`GV`/`OTH`, so the runtime reuses `rules.veh.*`), `TIME_ZONE` → `tz` (`24h`/`peaks`/`day`/`late`/`other`), `EFFECTIVE_DAY` → `eday` (`all`/`exc-sun-ph`/`sun-ph`/`other`) — deliberately not `hours`/`days`, which hold buslane's free text and Y/N mask. An unmapped code falls to the catch-all, never dropped. ⚠️ 4,345 of the 5,198 `OTH` rows carry no `REMARKS`, so there is nothing to classify them by — `OTH` ships as `OTH`. There is no `BOUND` field, so NSR lines are not offset to a kerb. NSR features carry `tippecanoe.minzoom` 12 (= `RULE_MINZOOM.nsr`): the always-on `rule-speed-hit` layer loads the z9–11 tiles for every visitor, and 20k lines there roughly quadrupled them for a layer nothing draws until z12. Each prohibition row is emitted **once per `kind`** it addresses (`PROHIBITION_KINDS` in `sign-layers.mjs`: `plb` · `ld` · `gv` · `all` · `other`) so a legend row is a plain `kind` filter; `kind` comes from coded `INC_VEH_TYPE` **plus the free-text `REMARKS` head** (`<who> Proh/ E <exceptions>` — learner drivers are only ever "LD Proh" with `INC_VEH_TYPE=OTH`, all-vehicle closures "AMV Proh"), and anything unclassified is `other` (DG, Bus, PC, a bare "Proh" — 141 rows), never dropped; the script prints the `other` heads so TD's wording drift is visible. Tile props are lean by design (`speed`, `hours`/`days`, `kind`/`inc`/`exc`/`part_time`/`all_days`, `veh`/`tz`/`eday`, `remarks`, `st_en`/`st_zh`; the vehicle codes are expanded at runtime via i18n `rules.veh.*`). Own cache-buster `rulesVersion` via `mergeTilesVersion` (geo.mjs) — both tile builders read-merge-write `tilesVersion.json` so neither clobbers the other. Spec with the code tables: `https://static.data.gov.hk/td/road-network-v2/dataspec/rdnet_dataspec.zip` (`BOUND` = side of the centreline in the digitised direction: 1 left, −1 right, 0 both).

   **The `cutoff` layer is the one derived extent** (`scripts/road-cutoff.mjs`, evaluated 2026-09): `CENTERLINE` edges public light buses cannot drive onto at all because TD's prohibitions and turn bans close every way in — Laguna City's Sin Fat Road is sealed by two "PLB Proh" routes that name neither it nor each other. 6. `build-sign-catalogue.mjs` (independent) is a thin CLI over **`scripts/catalogue/`** (`sheets` constants · `render` PDF→SVG/trace · `grid` lattice · `ocr` · `names` · `variants` · `normalize` · `extract` · `store` · `aliases`). It reads each TD **Index Plan** page (a table of `[No. | Symbol | Description]` column-groups) and writes `public/signs/<CODE>.png` + `app/data/signCatalogue.json` (`{ tier, group, desc?: {en}, alias?, superseded? }`). The PDFs are **vector** (a MicroStation DGN export — `mutool trace` shows ~55k linetos, zero text ops), so the page is rendered FROM its SVG and the grid is read straight from path geometry, not hunted for in pixels. Everything transient (page raster, trace XML, crops, montages) lives in `data/raw/.sign-cache` and is swept per sheet — under per-tag names in the working tree it would otherwise pile up (266 MB observed) where the old single fixed `/tmp` name self-limited. `renderPage` hands downstream code a **memory-mapped `.mpc` copy** of the page, not the PNG: every cell crop re-decodes its whole source, and at ~32 Mpx that is ~196 ms from PNG vs ~10 ms from MPC — four to six crops per cell over ~150 cells × 16 sheets made it about two thirds of the run (~50 min → ~17 min, byte-identical output). `--propose` stages under `data/raw/sign-recovery`. **`--rebind TS296=TS256,…`** is the third reviewer override (beside `--reject` and `--variants`): "this crop is right, the NUMBER it was read under is wrong". It is applied to the OCR read itself, before the dup/monotonicity/superseded/name checks, so the name cross-check scores the crop against the REBOUND code's entry and a mistaken rebind surfaces as `disagree`/`code-misread` instead of shipping quietly; it also overrides the merge-run "leave an existing code alone" skip, since a rebind usually REPLACES a wrong plate. It cannot express "only the first of two rows that read alike" — where two rows collide (253 misread as 293, alongside the real 293) leave it alone: the misread withholds and the genuine row still stages. The cardinal rule holds: "a missed sign degrades to a dot — a *mislabelled* sign must never ship."

   - **Render from SVG**: `mutool draw -F svg` emits the page as SVG (viewBox in PDF **points**); `rsvg-convert -z 8 -b white` renders it to a crisp ~6736×4763 raster (vector signs AND the ~13 embedded-image ones). **`-b white` is mandatory** — rsvg's default transparent background composites as BLACK in every downstream grayscale op (OCR threshold, symbol trim/flood), erasing the page. One render per sheet.
   - **Vector grid (point-space) + actual-divider crops**: `mutool draw -F trace` gives the ruling-line geometry in the SAME points (no DPI scaling). **Columns** from full-table-height vertical rules → the `[No.|Symbol|Desc]` lattice (origin/pitch/widths) measured per sheet; **rows are per-group** (horizontal rules spanning that group's width) so a per-group **rowspan** reads as ONE row (binds the informatory sheets 601-700, 2601-2717, 3601-3705, 3811-3936). Each sign's crop box uses **that group's OWN dividers** — symbol-right = the group's next full-height rule — *not* a global median width. (The median-width box was the sliver bug: on rowspan sheets it bled past the real Symbol|Description divider into the description column, so the trim couldn't tighten and the sign came out a wide sliver; a measured median is now only the fallback for a title-block group whose dividers were interrupted.) The **Description** cell runs from symbol-right to the next group's No-left, hard-bounded by the lattice pitch so the last group can't run on into the notes/title block. Crop coords = `point × 8`. A **group separator is a doublet** (two rules ~3 pt apart); its centre is the lattice position but a cell's edge is the doublet's *inner* rule (`columnModel` keeps each cluster's `lo`/`hi`) — cropping from the centre left the inner rule 1.4 pt inside the No. cell, past the 0.8 pt OCR inset, where tesseract read it as `(`/`{`/`f`.
   - **OCR bind**: the printed `No.` is read by `tesseract --psm 6` per cell (two binarisations — fixed-threshold, then OTSU+close — the second short-circuited once the first yields an in-range code; whitelist digits + L/T/R). The band is anchored on the cell's **ink**, not its top edge: a rowspan / "(DOUBLE SIDES)" cell prints its number vertically CENTRED, so the old fixed 18 pt-from-the-top crop read blank and lost the whole row. Two insets do two jobs here, and conflating them costs reads both ways: `NO_TRIM_INSET_PT` (2.0) is the window the ink is *measured* in — it must clear the border rule, or the trim latches onto the rule and calls the whole cell ink — while `NO_INSET_PT` (0.8) stays the crop actually fed to tesseract, because the No. column is only ~20 pt wide and its digits nearly fill it. The measured anchor is then backed off by the trim inset (floored at the crop inset), since the measurement window starts that far in and would otherwise slice the tops off a normal cell's digits. Measured against the old fixed crop: (TS 2601 - 2717) +11 reads including all seven double-sided rows, (TS 506 - 600) net zero. If the ink still spans >90 % of the cell the anchor is untrusted and the old top-of-cell crop is used. The symbol is cropped from the SAME row band so code and pictogram can't desync. Tesseract's input crop is staged in **`data/raw/.sign-cache`** (NOT `/tmp` — some sandboxes block a spawned tesseract from reading `/tmp`; magick is unaffected). A third recipe **C** runs when A and B read nothing in range: `-l snum`, the **digits model Homebrew's tesseract bundles** (`requireModel` in preflight), on a 300 %-upscaled, dilated crop, no whitelist. The two models fail on *different* digits — `eng` reads the sheets' thin CAD **7** as `1`/`(`/nothing (774 → `4`, 777 → `T`; the 1→7 rescue can undo only one such digit) while `snum` reads every 7 on 701-805 (84 of 110 rows vs eng's 17) but turns 8 into `B` and 1 into `l`/`jI` — so snum is a fallback here and a **second opinion** in `extract.mjs`: when eng's read is a dup or its name verdict is not `agree`/`fill`, `ocrCodeSecondOpinion` reads the cell with snum, and the snum code is taken only if it differs, is unseen, and the Description backs *it* (`agree`/`fill`) — the same evidence bar every shipped code already meets (832 read as 852 by eng and 835 as 834 were "unreadable" exactly this way). Only snum's FIRST token counts, and only when it is bare digits: its rendering of the "(TC …)" line (`tTC 418D`, `TC 431 D`) can leave a bare 4xx figure that would pass a 4xx sheet's range gate. The Description OCR therefore runs *before* the dup check now (one more tesseract call per skipped row in merge mode).
   - **Name cross-check** (`names.mjs`, the second bind): the row's Description cell is OCR'd (`-l eng`; the column is English-only on every sheet) and matched against the vendored `data/sign-names/descriptions.json`. Verdicts, in order: **`digit-conflict`** (digit runs differ — human gate, ship neither wording; this precedes the score because Levenshtein barely notices "10am-8pm" vs "10am-9pm" at ~0.97, and on the time-plate/limit families the digits ARE the meaning) → `agree` (our read equals the list's once normalised, or wholly contains it — ship OUR wording, **word-repaired**) → **`ocr-debris`** (a repaired word is still nowhere in the reference corpus — ship the list's wording) → `fill` (≥ 0.6, ship the list's wording) → **`code-misread`** (the name matches a *different* list key at ≥ 0.85 → **withhold the pictogram**; this is the detector for a digit misread that would otherwise ship a coherent crop under the wrong code — real ones are 20-40 out, because OCR confuses a digit's shape: 253 read as 293, 2639 as 2659) → `shift-suspect` (the match is ONE number away — never withholds, because the reference is a hand transcription that slips rows; it lists the sheet's verified 2629-2634 as 2630-2635, so that whole stretch matches its successor) → `disagree` / `no-list` (ship the pictogram, no desc). A read our OCR merely *contains* is corroboration, not a mismatch — the reference abbreviates TS2148 to `"NO STOPPING" ZONE` where the sheet prints `END OF PLB "NO STOPPING" ZONE`. **Word repair** exists because `agree` ships our wording through two deliberate blind spots: `normalise` DELETES every parenthetical before scoring (so `(SCHEDULED SFRVICES)` scores identical to `(SCHEDULED SERVICES)`) and containment tolerates up to half our read being text the list has no word for — between them 102 of 1,071 `agree` rows differed from the list and ~a third shipped visible garble. So the read is aligned to the list WORD BY WORD (Needleman-Wunsch, positional — a nearest-word-anywhere match would "repair" `ROUTE 3` into `ROUTE 5`) and any word within 2 edits takes the list's spelling; a word further off is OURS and the sheet's phrasing stands; nothing the list has and we did not read is inserted (that is `fill`'s job, and a shorter read is not an error). Guards: never across differing digits, and never on a **case-only** difference unless the word carries a digit — the list transcribes `PUBLiC`, but `1Km`/`2KM`/`11M` are OCR uppercasing SI units. `shippable` folds en/em dashes to `-` **before** its filter, or the sheets' `7am — 7pm` ships as `7am 7pm`: `normalise` had always folded them for the COMPARISON, so those rows still scored `agree` and only the shipped text lost the range (45 of 1,143). What repair cannot place is the debris test: a kept word absent from **every one of the 1,329 descriptions** is noise (`CVDOECOMWAVS`, `BTeuUT`, `NIDOCTIANES`), because road-sign English is a closed vocabulary — 34 of 1,071 rows, all genuine, and those fall back to the list's wording as `ocr-debris` (still `backed` in `extract.mjs`: the description matched its own code, only our transcription of it was noisy). 66 repaired + 34 downgraded on the pass that introduced it. The list has **no bare key for a "(DOUBLE SIDES)" row** — only `<n>L`/`<n>R`, identical text — so a bare base falls through to its faces, and `TS2701U/N/L` map to `2701-URBAN/-NT/-LANTAU`.
   - **Double-sided rows** (`variants.mjs`): a rowspan taller than 1.6× its group's median holds two stacked plates, one per face. The silhouette's widest interior gap is the cut; each half's facing is measured from its own taper (chevron-ended plates lose coverage at the pointed end), because the order is **not** fixed. **The taper is weak evidence**: scored against RSF's own `TS_<n>L`/`TS_<n>R` plates it got 11 of 16 rows right and had TS2629, TS649, TS651, TS653, TS659 backwards (corrected on commit). The earlier reading that "601-700 has 649/651/653/659 top=L" was that same heuristic written down, not a second opinion — every one of those four was a swap. Halves stage as `<code>__top/__bottom.png`; `verify.png` prints the measured face beside the source row, so **`--commit` IS the confirmation**, and **`--variants TS2663=RL`** (top,bottom) overrides it. A bare write-through rebuild has no review, so there the heuristic alone ships **no** face — only the base — and an unresolved half is dropped, never guessed. **The bare base is still emitted** (from the top plate) — TD installs it too (TS694 34 features, TS3643 87, TS3651 59, …), so withholding it would lose ~280 installed features. The vendored *name* list gives L and R identical text and so cannot check this assignment — but RSF's L and R **plates** are different images, so the `audit-sign-images.mjs` oracle can: normalise both halves, score each against both suffixes, and take the cheaper of the two pairings. A swap is unmistakable (TS651 `top→R` 0.078 vs `top→L` 0.547) and shows up independently as *both* shipped faces scoring ~0.42-0.56 where a correct row has at least one at `agree`. That check is not yet wired into the script — run it before trusting a face, and keep the human gate as the final word. Two plates can nearly touch: TS3650/TS3651 sit **5 px (0.6 pt)** apart, under `GAP_MIN`, and their outlines are open at the corners so the flood leaks into the plate and `silhouetteOf` falls back to a solid rectangle, which has no gap at all. So when the silhouette is `solid` the gap is searched on the **ink mask** (`inkMask`, threshold 60 %) of the same trimmed image, and a gap **flanked** by two rows that each span ≥ 90 % of the width — one plate's bottom border facing the next one's top border — is accepted at ≥ 2 px (nearest the middle wins); an unflanked gap still needs `GAP_MIN`. `pointing()` is unchanged (rectangles measure `null`), so those faces are the reviewer's call: on this family the sheet prints top = R, bottom = L (TS3643, TS3649, TS3650 and TS3651 all committed `RL`, each confirmed against RSF's L/R plates — TS3643 scores `top→R` 0.05 against `top→L` 0.31).
   - **Suffix aliases** (`aliases.mjs`, chained after the build): every installed `TS<n><L|R|T|B|F|U|N>` that has no plate of its own but whose base does gets the base pictogram plus `alias: <base>` — ~963 installed features.    - **Superseded**: grey row shading is the sheets' own legend for "SUPERSEDED OR DELETED". Left/right are deliberately untouched (TS560's end ticks are drawn on the sheet).
   - **Misread defenses** (NOT a GML filter — the catalogue is the Index Plan's set of DEFINED sign types, a *superset* of the installed `DTAD_TS_ABV_PT.gml` inventory, so filtering against GML would wrongly drop real defined-but-uninstalled signs): a **range gate** (a read must parse inside the sheet's printed range, dropping the out-of-range `(TC …)` reference line and stray digits) + a per-group **monotonicity warning** (the No. column is sorted; an out-of-order read is logged) + a **duplicate warning** (the same code twice on one sheet means one of the two rows is misread, and the one kept may be the wrong one — that is how a correct pictogram lands under its neighbour's number) + the name cross-check above + the human gate below. The No.↔pictogram bind is checked separately and on demand by `audit-sign-images.mjs` (above) — every defense in this list reasons over TEXT, so a crop lifted from the wrong row satisfies all of them. A **blank row is not a sign**: TS360 and TS853 are greyed, empty rows on their sheets, yet the catalogue carried a neighbour's plate under a *different* neighbour's wording for both (TS853 = TS852's plate + TS855's text) — deleted. Deleting a code leaves the derived artefacts stale (`signGroups.json`, both PMTiles, `public/signs-stacked/`) until the next `data:build`; the extractor itself self-heals, since a blank row yields no crop to re-add.
   - **Human gate** (`--propose` / `--commit`): recovery stages crops + a `verify.png` (each candidate's SOURCE `[printed No. | pictogram]` strip, labelled with the OCR'd code, **its verdict**, and any split faces) + a `manifest.json` under `data/raw/sign-recovery`, writing NOTHING to the repo. The verdict labels turn review into triage — look hard at `digit-conflict`, `code-misread`, `disagree` and every split — before `--commit [--reject TS#,TS#] [--variants TS#=RL]` promotes the approved crops.

The VLM was dropped outright, not just made optional: the Description column is English-only, so its `zh` was sign-face text (`停`, `Bus巴士`, `3tonnes公噸`) or a time range, and its `en` was row-shifted (TS162-165, TS179-184 — TS182 shipped as "CYCLES ONLY" where the sheet says ONE WAY TRAFFIC). Coverage of installed features: 86.7 % → ~87.6 % with aliases + splits. The **ceiling is 87.8 %** — `TSSEPA` is 21,907 features (12.2 % of the inventory), a separator marker with no pictogram, so don't chase a higher number.

Key dataset fact: **`SIGNID` exists only on the `traffic-sign-abbreviation` class.** Pole classes (`DTAD_TS/PS/DS_POLE_PT`) have no `SIGNID` and no sign content — they are bare posts (but `DTAD_TS_POLE_PT` shares its `GG_NAME` with the signs on it, which is how step 3 tells that two groups are two faces of one pole). Abbreviation points are the drawing's *label* positions, a median 2.3 m from their pole. No class records a sign's facing (`DTAD_TS_PLATE_LINE` is only the full line-work of custom directional plates — ~19k features, 3 GB — not a plan-view plate mark). Only abbreviation features can resolve to a pictogram; everything that maps to category key `none` (poles) is never rendered.

## Runtime architecture (the part that needs multiple files)

- `useSignCatalogue.ts` is the hub: loads `signCatalogue.json` + `signDescriptions.json`, exposes **`signDescription(signId, locale)`** (curated zh/en override → curated en → extracted `desc.en` → null, following an `alias` to its base sign; English shows verbatim in the zh UI when no zh override exists — the catalogue holds no Chinese by construction), derives `codesByTier`/`codesByGroup`, and exports **`categoryKeyExpr`** — one static MapLibre expression mapping any feature to its category key: a catalogued Index-Plan group (`regulatory|warning|informatory|supplementary|temporary`), else by tile `category` → `tourist`/`other-traffic`, else `none`. `TIER_LOD` defines per-tier `minzoom` and the top-of-ramp `icon-size`; `SIGN_FIRST_SIZE` is the shared normalised height every tier shows at its reveal zoom.
- `useSignCategories.ts` = legend/filter rows + colours, keyed by those category keys.
- `useTrafficLayers.ts` = singleton state: `enabled` per category, `selectedSign`, and `mapFilter` — the one filter every layer rides. Category mode: `['in', categoryKeyExpr, enabledKeys]`. Sign-ID mode: `['in', SIGNID, picks]`, **widened** to `['any', that, ['match', STACK_ID, companionPosts, true, false]]` once the lazily dynamic-imported `signGroups.json` index resolves (`loadGroupIndex`, fired by TrafficMap when sign-ID mode is active) — so a matched sign pulls in its co-located post-mates and renders as the **whole signpost**, not a lone plate (companions already carry `STACK_INDEX` + collapsed geometry in the full archive, so they stack for free). `match` (not `in`) on `STACK_ID` for the O(1) lookup — a common sign sits on thousands of posts (`TS860`: 5,332). Until the index loads (or for a sign on no multi-member post) it stays the plain `in`. The allowlist has **two write shapes**: `filterToSigns`/`filterToSign` REPLACE it (the exclusive "show only this sign" of `SignPopup`), while `addSigns`/`removeSigns` add and subtract a contribution without clearing the rest — the road-rules rows use those, so several rows read as a union of their plates. Hence **two** active-state predicates, both kept: `isOnlySigns` (equality, for the exclusive buttons) and `hasAllSigns` (containment, for a union member) — collapsing them lights an exclusive button up for a filter that merely includes its code. `removeSigns` returns to `category` mode when the allowlist empties, because an empty allowlist in sign-ID mode is a filter that shows nothing and every layer (the dot included) rides it.
- `TrafficMap.vue` builds the map: an always-on `sign-points` circle (coloured by `categoryColor` = `match` on `categoryKeyExpr`) as the baseline marker; per-tier `sign-tier-N` symbol layers for **lone** signs (`minzoom` = tier minzoom, `icon-size` ramps from shared `SIGN_FIRST_SIZE` up to the tier size, collision fully disabled) plus the single `sign-stack` layer for signpost members (see Signpost stacking); a `sel` GeoJSON highlight overlay (halo+dot+icon) moved to the top on every selection; click collects all signs in a 6px box, de-dupes, and cycles through them on repeat clicks. **Two vector sources** are registered (`signs-lod` = thinned overview archive, `signs-full` = retain-all archive); the sign layers read the one `sourceForMode(filterMode)` picks — `signs-lod` in category mode, `signs-full` in sign-ID mode. MapLibre can't repoint a live layer's source, so a `filterMode` flip calls `removeSignLayers()`/`addSignLayers(source)`; the sign layers are inserted **beneath the overlay stack** (`beforeId: 'sel-group-glow'`, the lowest overlay) so the selection/group overlays are structurally always on top across the swap (no per-selection `moveLayer` needed). **Signpost stacking**: a post's members (every `GG_NAME` face sharing a pole point, keyed by `STACK_ID`) are collapsed at build time (step 4) to one anchor, each carrying its face's bearing, so they're a **rigid post**. Lone signs render in the per-tier `sign-tier-N` layers; every **stacked** member is excluded from those (`['!', ['has','STACK_INDEX']]`) and instead drawn by the one **`sign-stack`** layer, because a post must be **one sizing unit**. That layer draws each member's `icon-image` from the **common-width** `signs-stacked` set (`['concat', ['case', ['has','STACK_INDEX'], 'signw-', 'sign-'], SIGNID]`; the lazy loader fetches `/signs-stacked/` vs `/signs/` by prefix), so plates keep their true aspect (wide→short, tall stays tall); offsets them with a data-driven `icon-offset` = `match` on **`STACK_OFF`** → `[0, STACK_OFF]` over a fixed grid (`OFFSET_STEP` 8 px steps up to `OFFSET_MAX`; baked per member in step 3) into a column (main on top, supplementary below); and sizes the **whole post by one `icon-size`** keyed on the primary tier (**`STACK_TIER`**, baked in step 3), all members revealing together at `STACK_MINZOOM` (= `TIER_LOD[0].minzoom`). Because every member shares that one multiplier and the images are width-normalized, the plates keep their **real-life height ratio at every zoom** — the earlier per-tier sizing scaled mixed-tier members differently and skewed it (the bug this layer fixes). The offset is in icon source-px so it scales with `icon-size` (the factor *cancels out of the spacing*) and rides `icon-rotate` (= the member's `FACE_BEARING`, uniform within a face), so each **face's column rotates rigidly** to its facing — a back-to-back pole's two faces — the forward face on the post facing, the no-entry face turned 180° (sides at 90°/270° when a pole carries more) — hang from the anchor in opposite directions, which is how the map shows that the signs on one pole face different ways. Lone signs' `icon-size` stays the per-tier ramp (fixing on-screen height); the width-normalized stacked images get their width fixed by the shared multiplier — the image encodes which dimension is pinned. **Group highlight**: clicking any sign in an assembly is treated as selecting the **whole post** — the single-sign `sel` overlay is suppressed for grouped signs (else only the clicked member would balloon and its halo would land at the post anchor, not the offset pictogram). Instead a `sel-group` GeoJSON source is filled with every member sharing its `STACK_ID` (gathered via `querySourceFeatures` on the active source — *not* the tier layers, which get hidden next, and a source query also survives re-clicking the same post; deduped by `STACK_INDEX`). Two layers — `sel-group-glow` (a generated glow disc) + `sel-group-top` (the pictogram) — re-draw every member at the shared **`EMPHASIS_SIZE`** (uniform, so a lone click and a group click enlarge alike, and one zoom-interpolate ⇒ no per-tier split) with `stackOffset`, so the whole post enlarges together. The selected post's base pictograms (now all on the `sign-stack` layer) are hidden via `stackFilter`'s `hideStack` arg (re-applied by `refreshSignFilters` on selection) so they don't show doubled under the enlarged copies.

- **Road-rules overlay** (`useRoadRules.ts` + TrafficMap + `LayerFilterPanel` section + `RulePopup.vue`): a third `pmtiles://` source (`rules`) drawn as `line` layers, the first non-point layers in the app. `RULE_ROWS` (legend order, colours, `rules.rows.<key>` labels; `SPEED_COLORS` colours speed lines by value, `NSR_VEH_COLORS` no-stopping lines by `veh`, each with a chip row under its legend row) is the runtime twin of `RDNET_RULE_LAYERS`/`PROHIBITION_KINDS`/`NSR_VEHICLE_TYPES`. **Two source-layers hold several rows each and are SPLIT by a tile property** (`ROW_SPLIT_PROP`: `prohibition` by `kind`, `taxi` by `taxi`); every other row still has `key === layer` and carries neither discriminator. The taxi rows deliberately use their own `RuleRow.taxi` field rather than reusing `kind`, because `prohibitionColorStops` is built from the rows that carry `kind` and would otherwise pick them up. **Every place that turns a clicked FEATURE into a row goes through `rowValueOf(layer, properties)`** — reading `properties.kind` directly was correct while prohibitions were the only split layer, but a taxi feature carries `taxi` and no `kind`, so a clicked Lantau band tested against the NT row: unpickable unless NT happened to be on, and mislabelled when it was. Beyond the split, the `plb` row owns **two** source-layers: TD's `kind: 'plb'` prohibitions AND the derived `cutoff` band behind them (`rowKeyFor` maps both to it, so one checkbox draws both, and the band's teal lives in `CUTOFF_COLOR` since it has no row of its own to hold it). A ban and the area it seals off are one answer to one question, so they are one row; each still keeps its own popup title and swatch, and the legend row carries two chips naming the two readings. State is `rulesEnabled` (`hk-signs:road-rules` in localStorage; every row is an opt-in reading, unlike the category toggles, **except `plb`, which is on by default** via `RuleRow.defaultOn` — the overlay's most useful reading and the only one that needs no colour scale to parse). `selectedRule` (a clicked line) and `governingRule` (the rule found for the selected SIGN). A row means **"draw this reading, and show the plates that announce it"**: `onRuleToggle` (`LayerFilterPanel`, the only user write path into `rulesEnabled`) unions the row's `ROW_SIGN_CODES` into the sign-ID allowlist on tick and subtracts them on untick, so ticking several rows shows all their plates and an untick is the same gesture undone — the map filter is already an `in` over the allowlist, i.e. an OR. It adds **only the toggled row's** codes: recomputing the union over every row that is on was tried and reverted, because `plb` starts on and so never fires the handler — it folded TS119/TS522 in on the first tick of any OTHER row, which expanded the filter unasked (ticking bus lanes added speed plates) and broke the undo (unticking that one row left plb's two plates instead of every sign). Per-row costs only that a row already on contributes nothing until toggled. It is driven from that handler and **not a `watch(rulesEnabled)`**, which would also fire on `mergeDefaults` writing a newly-added row key and on mount, where the `plb` default-on row would filter a first visit down to its two plates. The four rows no plate links to (`pedzone`, `proh-gv`, `proh-all`, `proh-other`) contribute nothing and leave the sign filter alone. `RulePopup`'s button is the narrower twin — a clicked 70 km/h line adds `TS175` alone where the row covers every speed value — and does **not** enable its row, because TrafficMap picks a rule only through `isRowEnabled`, so a clicked line's row is necessarily already on (a write there would be dead code AND a second writer of `rulesEnabled`). Getting the lines over the *unfiltered* sign map is therefore two steps: tick the row, then the Category tab (the lines stay — `rulesEnabled` is independent of `filterMode`). ⚠️ `mergeDefaults` only fills in MISSING keys, so changing an existing row's default is invisible to anyone who has already loaded the app — a default change needs a NEW row key (why the merged row is `plb`, not `proh-plb`). Each kind is **two layers**: `rule-<layer>-hit` (14 px, `line-opacity` 0, **always visible**) and `rule-<layer>` (toggled by `visibility`; a split layer additionally by an `in` filter over its enabled rows' values — `enabledKinds` for prohibitions, `enabledTaxis` for taxis). The hit layer is load-bearing twice: click tolerance on a 1–6 px line, and **keeping the source's tiles resident when every overlay is off** — MapLibre only requests tiles for non-hidden layers, and the sign popup's "applies here" lookup (`SIGN_RULE_LINKS`: a TS175 → the nearest `speed=70` line within `SIGN_RULE_RADIUS_M` 15 m; a no-stopping plate → the nearest NSR line of the same `veh` **and** `tz`, via `querySourceFeatures` + `pointToLineMetres` in `app/utils/geo.ts`) needs them loaded. ⚠️ **Residency is not completeness, and the lookup does NOT resolve at every zoom** — MapLibre's `used` flag is per *source* (the always-on `speed` hit layer keeps the tiles coming from z9), but what is IN a tile is set per feature by `tippecanoe.minzoom`. So `nsr` (z12) resolves nothing below z12 — all **28 no-stopping codes, ~6.5k clickable signs, 0 %**; quantization costs the other three linked layers a little at the floor, **83.5 % at z9 and 95.1 % at z10** against a ~97 % ceiling (measured territory-wide; the residue is signs genuinely >15 m from any TD line). This is a withheld answer, never a wrong one — `SignPopup` hides the block outright, so a miss reads exactly like a sign with no rule. **Do not "fix" it by gating the lookup to null below some zoom** (that is already the output, minus the 83.5 % it gets right), and **do not raise a linked layer's `tippecanoe.minzoom`** — below its `RULE_MINZOOM` the lookup is that layer's only consumer, so the bytes and the feature go together (measured: `prohibition` is ~48 % of the z9/z10 tiles, but those are 82/100 KB territory-wide and are fetched only by a user who zooms to the floor — MapLibre 5 has no parent prefetch, and the map lands at z11). The real improvement, if one is wanted, is a third `governingRule` state distinguishing "no rule here" from "can't tell at this zoom". `cutoff` gets **no hit layer** — it is only ever a 4–22 px band. `taxi` DOES get one, but a **toggled** one that follows its row's visibility rather than being always on: its `area`/`dest` features are bands, yet a designated `route` draws at exactly `RULE_LINE_WIDTH`, so it needs the tolerance every other thin line gets, while nothing requires its tiles kept resident (no taxi plate drives the "applies here" lookup). ⚠️ **Hiding a layer saves a bucket and a hit-test, never bytes** — an MVT tile carries every source-layer, and the always-on `rule-speed-hit` already pulls this source from z9, so the taxi features ship to every visitor with all three rows off. Measured: z11 (the landing zoom) went 16.9 → 31.6 KiB per tile, z10 16.7 → 38.9 KiB, archive 3.88 → 5.16 MB. The only lever on that is a SEPARATE archive and source registered on first tick (the `signs-lod`/`signs-full` precedent) — not a `minzoom` bump, which would move the cost and cost the reading its point. Rule layers are added **before** `addSignLayers` on the same `sel-group-glow` anchor so a filter-mode flip re-inserts the sign layers above them (roads under signs), and their ids stay **out of `signLayerIds`** — the click handler's `featureKey` assumes point geometry. Clicks: signs first; only when no sign is hit do the hit lines get queried, and only rows the legend has on are pickable (the hit line exists regardless). `TS174` (50 km/h) links to nothing on purpose — the default limit has no rows — so its popup states that instead. **Every link is held to a measured ≥ 90 % within-15 m hit rate** over its code's installs at the tile (pole) position; for no-stopping that bar is on `veh` + `tz` together, because a veh-only match would hand a 7am–7pm plate the 24-hour line next to it. 28 codes pass; the 7am–7pm and 8–10am & 5–7pm all-vehicle zones do **not** (TS2133 18.5 %, TS2134 23.6 %, TS2230 17.1 % — TD codes most of those kerbs `OTH`), nor TS183 (clearway), TS2138, or the END-of-zone plates (a terminator says where a zone stops) — the numbers are in the `SIGN_RULE_LINKS` comment. Re-measure before adding a code. NSR draws dotted (`line-dasharray` `[0.1, 2]` + round caps) from z12, distinct from prohibition dashes. `cutoff` is drawn FIRST (under every rule line) as a wide 35 %-opacity band with **butt caps** — round caps of adjoining edges stack into bright dots at every junction — and its popup swaps the source line for `rules.cutoffSource` (worked out, not a posted rule). The `taxi` bands draw first of all (beneath `cutoff`), in the licence colours, with the same butt caps and their own `rules.taxiSource` line. ⚠️ `access` varies **width and opacity, never the dash pattern** — `line-dasharray` is the one line paint MapLibre will not take a data expression for, and splitting this into two layers to dash one would double the toggling and the click handling for a cosmetic difference; so an operating `area` is widest and faintest, a `dest` as wide but brighter, a `route` narrow and brightest. Each width rides in the interpolate's STOP OUTPUTS, as `plateSizeFactorExpr` and the bus-lane offset do. Only the `taxi-nt` row carries chips, because it is the only one that draws all three readings. A bus lane's `line-offset` puts it on its `bound` side; the factor rides in the interpolate's stop outputs (zoom can't sit under an outer `*`).

- **Rule notes** (`useRuleNotes.ts` + `app/data/ruleNotes.json` + `RuleNoteBlock.vue`/`RuleNotePopup.vue`, surfaced in TrafficMap and inset in `RulePopup`): curated, bilingual annotations on the overlay, for the case where **TD's data states a rule that a TD arrangement has relaxed, and the relaxation exists in no field of the dataset**. The overlay's extents stay verbatim (see the Invariants) — a note says so in place rather than bending the data. The shipped case: every one of the five roads TD designated in 2021 for public light buses to reach the Vehicle Examination Complex (青荃路 via 青衣北橋, 青衣北岸公路, 長青公路, 青衣西路, 西草灣路) carries at least one unconditional `PLB Proh` row **created after that opening** (8 of the 12 such rows postdate it — 8152/96593/164349 2021-10-12, 8383/93040/96829 2022-03-23, 8746/97220 2022-05-18; the other four date from 2011), with `EXC_VEH_TYPE` `NA` and TS119 plates standing on the ground — so the ban is real and correctly drawn, but the map also shades the complex's own access roads as `cutoff` ("cannot enter at all"), which the designated route contradicts. The note is the honest fix; **do not add the exception to `closesFor`** (it has no data to key on, and `E WP` is deliberately treated as still closed). Mechanics: notes are edited **independently — no tile rebuild, no pipeline re-run**, like `signDescriptions.json`, and their prose lives in the JSON rather than i18n because it is content, not UI chrome. A note's `covers` clauses are **declarative** (`layer` + optional `kind`/`st`/`via`) so the same clause compiles to BOTH a MapLibre filter (`coversFilter`, for the highlight) and a JS predicate (`coverMatches`, for "does this clicked line carry a note?") — the `ruleLinkFilter`/`ruleLinkMatches` twin pattern; keep the two in step. `via` is a substring test against the cut-off band's comma-joined sealing streets, and both sides go through `to-string` so a null property misses instead of throwing. Two entry points, one answer: a pin (`rule-note` symbol layer, one per `at` position — a designated route runs for kilometres, so one marker would sit nowhere near most of it) and the covered lines themselves, both lighting the same highlighter band (`rule-note-hl-<layer>`, added FIRST at the `sel-group-glow` anchor so it sits under every rule line, and yellow because no row is — a wide translucent band under the thin amber speed line) and showing the same `RuleNoteBlock`. Pins live in the **overlay bucket**, not with the rule lines: everything else inserts beneath `sel-group-glow` and the sign layers are re-inserted there on every filter-mode flip, so a pin added with them would be buried by signs. Pins **win a contested click outright, ahead of signs** (a pin is a small deliberate target drawn on top), and show only while one of the note's `rows` is on.

### Invariants that caused churn — keep them

- **Rule extents come from the IRNP layers, never from sign points.** The data to walk a limit along the network from a sign does not exist (no terminator semantics, facing ungraded, corner poles ambiguous) and TD already publishes the answer — see pipeline step 5 for the numbers. If a rule looks wrong on the map, the fix is in TD's data or the `kind` derivation, not a heuristic over signs. The `cutoff` layer is the one derived extent, and it is derived from those same TD bans over TD's network — a wrong area means a ban `closesFor` misread (check the build's top-areas printout), not a reason to reach for sign points.

- **Taxi operating areas are CURATED from the law, and the plates audit them.** The `taxi` layer is the one reading in the overlay whose extent is not TD's own geometry, because TD publishes none — see pipeline step 5. Its extent lives in `data/taxi-zones/areas.json`, cited to Cap. 374E Sch. 7 and TD's boundary map, and its popup says so (`rules.taxiSource`, the twin of `rules.cutoffSource`) rather than crediting the road network. The 241 `TS329` / 8 `TS569` terminators and the per-colour stand plates go through `audit-taxi-zones.mjs` and are **never** an input: a terminator says only where something STOPS, which is why the same plates are also barred from `SIGN_RULE_LINKS`. Precisely: **no road's classification is computed from a plate** — the classifier never reads one. Where a boundary runs INSIDE a district, TD's raster is no better than a kilometre, so a human placed the ring and (for `ma-on-shan` only) read its latitudes off the TS329 line first; the clause records that. Verification steering a hand-drawn line is not an extent derived from points. TD's boundary map is a **raster** — it cannot be traced, so do not reach for the Index-Plan extractor. Where TD publishes a destination but not the road to it, the map UNDERDRAWS: a withheld answer, never a wrong one, exactly as with the sign→rule lookup at low zoom.

- **Collision is disabled** (`icon-allow-overlap`/`icon-ignore-placement` always `true`) because every point is a real installed sign with a 1:1 ground meaning, so MapLibre must never drop or nudge one for a neighbour. The old "constant `icon-size`, never zoom-interpolated" rule existed *only* to stop growing icons from collision-hiding already-shown signs — with collision off that coupling is gone, so it was deliberately retired. Do not reinstate per-zoom collision.
- **Sign icons rotate by `FACE_BEARING`, not the raw TD `ANGLE`.** TD's `ANGLE` is the MicroStation symbol-cell rotation ("same as Ustn angle" per the dataspec): it lives in the −90°…+100° band (a text-readability rotation), is unrelated to the road (flat against the road tangent when measured HK-wide), and 59 % of same-code signs <30 m apart share one — opposite carriageways look identical when fed to `icon-rotate` (commit `fde0258` proved this, `42c343a` reverted it). The pole's `ANGLE` is equally unrelated to the road. `FACE_BEARING` is the build-time facing from `compute-bearings.mjs` (Data Pipeline step 2): **absolute** where a directed Road Network centreline hosts the pole (97.7 %), via the one-way / nearside rule under drive-on-the-left, then **turned 180° for the no-entry family** (`AGAINST_TRAFFIC_CODES`) because that plate speaks to the wrong-way driver; relative-only on the 1.4 % marking fallback (`FACE_ABS` 0); the 0.8 % with neither carry no `FACE_BEARING` at all and render upright. It is a derivation nothing can grade — no published source says which way a sign faces — and the corner-pole host choice is its measured weak spot (step 2). Earlier inputs: `DTAD_RD_AL_LINE` covers only ~178 km; `DTAD_RD_MARK_LINE` (lane markings) gave the 180°-apart invariant but no direction; `DTAD_TS_PLATE_LINE` is only the line-work of custom directional plates.
- **`icon-rotate` is `FACE_BEARING + 180`, not the bearing itself.** The plan view draws each plate as if **tipped flat onto the map**, and a vertical plate tipped BACKWARD (away from the traffic it addresses) lands face-up with its top edge behind it — so a south-facing plate reads **upright** on a north-up map, which is also what its driver sees, since they travel at `FACE_BEARING + 180`. Rotating by the bearing itself tips the plate FORWARD: the face ends up buried in the ground and the artwork is drawn through the plate's back — upside down, and left-right reversed for everyone who can actually read the sign (a southbound "EXPRESSWAY" plate came out mirrored; the only viewer it read upright for was the driver going the other way, who sees the plate's back). The `+180` rides **inside** the has-`FACE_BEARING` check, never after a `coalesce` to 0, or the ~0.8 % with no bearing would render upside down instead of upright. Everything rigid to the icon follows the flip: a face's `STACK_OFF` column now hangs along its facing (the post's primary reads at the TOP of the on-screen column, where its `STACK_INDEX` 0 says it is — before the flip the column was drawn upside down too), and the selected sign's facing bar marks the plate's base on the traffic side.
- `icon-opacity` is **zoom-faded** (0.55 at z13 → 0.9 at z17, held at 0.9 — never fully opaque) on the tier layers. With collision off, signs pile up zoomed out and can still overlap at max zoom; the hard fade lets the stack show through while crowded, and the permanent 0.9 ceiling keeps residual high-zoom overlaps legible-through. Per-*sign* "is it overlapped" opacity is **not expressible in MapLibre** (collision can only hide, not report) — don't attempt it; this fade-by-zoom plus the constant ceiling is the deliberate substitute.
- `icon-size` now ramps per tier: every tier starts at the **shared** `SIGN_FIRST_SIZE` at its reveal `minzoom` (normalised on-screen height — pictograms are all 120px tall) and interpolates up to the tier's `size` at `MAX_ZOOM`. Keep the *first-display* size shared across tiers (visual consistency); only the top-of-ramp size is tier-specific (legibility for complex signs). The ramp is then multiplied by `plateSizeFactorExpr` (`PLATE_SHRINK` 0.85 for codes in `signShapes.json`, else 1): because every pictogram renders at a shared *height*, a solid full-bleed square (the blue "P") covers ~100% of its box while a circle covers only ~π/4 ≈78%, so the square reads heavier — the shrink rebalances visible area. **The factor folds into the interpolate's stop OUTPUTS, never as an outer `['*', …]`** — MapLibre only allows a `['zoom']` input directly under a top-level interpolate/step. Lone signs only (the `sign-tier-N` layers); stacked posts keep their own width-normalized sizing.
- The always-on dot is the fallback so a sign is **never invisible** below its tier's minzoom. This was tried both ways; the always-on dot won because the alternative left a confusing zoom band with neither dot nor sign.
- All instances of a `SIGNID` are in exactly one tier ⇒ one appearance zoom.

## Deployment

Static (`corepack pnpm generate` → `.output/public`). **The host MUST serve HTTP `Range` (`206 Partial Content`)** — PMTiles reads both archives (~24 MB overview + ~46 MB full) in byte-range slices, so a given view only pulls the slices it needs. GitHub Pages, Cloudflare Pages, Netlify, S3+CloudFront, nginx all do. `nuxt preview` does **not** (returns the whole file with `200`) — local checks only.

Commit style: gitmoji, phase-tagged (see `git log`).
